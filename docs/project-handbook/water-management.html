This document describes the implemented water-management workflow in Agro Core. It covers irrigation sectors, soil-moisture monitoring, irrigation scheduling and execution, water usage, water sources, hydraulic infrastructure, water quality, water balances, maintenance, and sensor verification.

The module records and compares operational information. It does not calculate an agronomic prescription, open valves automatically, or replace technical review.

Operational workflow

  1. Configure a sector. A manager associates a sector with a block and records its irrigation system, water source, area, measurement unit, measurement depth, and optional sensor.

  2. Set technical limits. The responsible technical user records the lower and upper moisture limits, the maximum age of a valid reading, and the technical basis. Limits are versioned when changed.

  3. Measure conditions. A user records a manual reading with its instrument, rainfall, drainage, and notes, or the sector receives a compatible sensor reading.

  4. Review conditions. The module classifies the latest reading as below range, in range, above range, stale, or without data when the required information is available. It does not infer an agronomic recommendation from that classification.

  5. Schedule irrigation. A manager creates a one-time plan with the target sector, planned date/time, duration, volume, assignee, technical justification, and execution instructions, or creates a recurring rule with a daily/weekly interval and start/end dates.

  6. Generate repeated work. Active recurring rules materialize each occurrence as a normal irrigation plan and farm task. The schedule/date uniqueness key and the daily generator prevent duplicate plans or tasks. The background job runs daily (default cron: 00:15 in the API server's time zone) and fills the next 30 days; managers can also preview or generate occurrences and pause, resume, edit, or cancel future generation. Set AGRO_IRRIGATION_RECURRING_CRON through the Spring property agro.irrigation.recurring.cron to change the job schedule.

  7. Generate and execute the task. The plan can generate one farm task. The assigned worker or an authorized manager records execution using a meter or a flow estimate. Overlapping executions for the same sector are rejected.

  8. Verify and preserve history. Actual volume and duration accumulate against the plan. Exceeding the planned amount requires a reason, and the execution is linked to an IRRIGATION_EVENT with optional photo evidence.

  9. Correct operational records. Authorized managers can edit water sources, quality analyses, hydraulic assets, balances, maintenance, and sensor checks. Updates are farm-scoped and use optimistic version checks to reject stale edits.

  10. Analyze usage. The Reports screen filters water usage by date range and sector/block, presents planned versus applied volume and measured versus estimated origin, compares rainfall and balance deficits, and exports the visible sector report as CSV.

Water-management records

Soil moisture

The supported units are volumetric percentage (VWC_PERCENT), gravimetric percentage (GRAV_PERCENT), and kilopascals (KPA). Units and measurement depths must match the sector configuration. Percentage values are constrained to 0–100; the module does not treat the three units as interchangeable.

Reading freshness is evaluated per sector using its configured maximum age. A stale or missing reading produces an operational warning rather than an automatic watering decision. Rainfall and drainage are retained as context for later technical review.

Irrigation execution and usage

Meter-based execution stores the meter unit and starting/ending readings. Flow-based execution stores the flow in cubic metres per hour and derives volume from effective duration. Effective duration subtracts recorded interruptions. Multiple partial executions can be recorded against a plan while the plan tracks cumulative actual volume and duration.

The module requires a variance reason when cumulative actual volume or duration exceeds the planned values. It rejects future timestamps, invalid meter sequences, non-positive effective duration, and overlapping executions for a sector.

Water sources and infrastructure

Water sources can be wells, reservoirs, canals, rivers, rainwater, or another source. Hydraulic assets can be pumps, valves, pipes, filters, meters, drains, canals, reservoirs, or other assets. Sources and assets may include coordinates and notes; assets can be associated with a block and a water source.

Water-quality records are linked to a source and may include laboratory references. The database validates pH from 0 to 14 and prevents negative analytical values.

Balances, maintenance, and calibration

Water balances are recorded by sector and date. The record can include rainfall, reference evapotranspiration, crop coefficient, root depth, available water, required volume, applied volume, and deficit. A sector may have only one balance for each date.

Maintenance can target either a sector or a hydraulic asset, but not both. Supported activities include filter washing, pump and valve checks, leak repair, meter calibration, drain cleaning, and other maintenance. Sensor checks retain the sensor, sector, date, calibration status, reference value, observed value, technician, and notes.

User interface

The Riego screen opens on Resumen. It shows recorded consumption, scheduled sectors, pending volume, scheduled area, maintenance pressure readings for the selected date, and the next scheduled irrigation. The pressure card shows an empty value when the date has no pressure reading. The map colors blocks by the status of their visible sectors. Search and field/status filters update both the map and the sector table. The layers button shows or hides the illustrative network in demo mode. On a connected farm it shows assets that have recorded coordinates. Select a colored block to open the details for its visible sectors. Programar riego opens the scheduling form for authorized users.

  • Sectores shows configuration, moisture history, and operational alerts.

  • Programación provides one-time and recurring schedules, task and occurrence generation, upcoming-occurrence preview, pause/resume/edit/cancel controls, and sector context.

  • Ejecuciones summarizes recorded volume, effective time and irrigated sectors for the selected filter. It counts meter readings and flow estimates separately. Open a record to review interruptions, variance, moisture readings before and after execution, and attached evidence. Exportar CSV exports execution records.

  • Sensores shows the readings recorded with sensor origin.

  • Infraestructura contains sources, quality, hydraulic assets, balances, maintenance, and sensor calibration checks.

  • Historial anterior opens the legacy irrigation events.

Mapas → Humedad del suelo shows the latest sector readings, their conditions, and the depth profile for the selected block. The summary average uses readings that share a unit. A block with several sectors shows their count and the traceability table retains the separate measurements.

The Reportes screen also includes a water-use report with period and sector/block filters, KPI cards, a sector comparison table, and CSV export. It reads the same farm-scoped irrigation records as the Riego screen and labels demo values as fictitious.

The demo mode uses local browser storage and clearly labels its initial data as fictitious. Real mode reads and writes through the server API.

Farm membership and manager permissions are enforced by the backend. Sensor device registration and raw telemetry ingestion are provided by the sensor endpoints and are consumed by irrigation sectors when associated.

Persistence and implementation evidence

The water workflows run native SQL through JPA's EntityManager in JpaSql. Irrigation uses PostgreSQL row locks for concurrent changes and retains version checks on management records. Transactions keep recurring schedules, generated plans and tasks, execution totals, and linked field events consistent. The water-use report reads the same stored plans and executions through native JPA queries. JPA persistence

Remaining gaps

  • Full approval, calendar, escalation, and notification workflows.

  • Automated meter/telemetry reconciliation and weather-service integration.

  • Complete hydraulic map showing sources, pipes, valves, drains, and relationships.

  • Permission policies for water-source, infrastructure, and technical-threshold administration.

  • Offline capture and synchronization for field operations.

Verification

The focused backend tests cover H2 API fixtures and the PostgreSQL execution and reporting paths. Run the PostgreSQL test with a configured PostGIS database.

./gradlew test --tests com.yourco.agro.IrrigationApiTest
./gradlew test --tests com.yourco.agro.IrrigationPostgresTest

The frontend irrigation workflow can be verified from frontend with:

npm run build
npm run test:e2e -- tests/irrigation.spec.ts -g "water management records"
npm run test:e2e -- tests/irrigation.spec.ts -g "recurring irrigation schedules"
npm run test:e2e -- tests/irrigation.spec.ts -g "water usage report"
