Interfaz en español de Agro Core, construida con React, TypeScript y Vite. El diseño toma como referencia las imágenes suministradas: tonos verdes, navegación lateral, tarjetas de información y mapas como centro de la experiencia.

Inicio rápido

Requiere Node.js 22.18 o superior y npm.

cd frontend
npm ci
npm run dev

Abrir http://127.0.0.1:5173. No se necesita el backend para explorar la demostración.

Para conectar datos reales, iniciar el API según el README principal y seleccionar Conectar mi finca. Primero se puede registrar una cuenta; después, iniciar sesión y crear una finca o solicitar acceso a su administrador.

El proxy de desarrollo envía /api a http://localhost:8080. Para otro destino:

AGRO_API_URL=http://localhost:8081 npm run dev

El inventario completo de endpoints y pantallas de nutrición está en docs/fertilization.md.

En modo real, el detalle de Análisis usa el perfil activo configurado para la finca; la capa Mapas → Nutrientes todavía usa un perfil provisional incluido en el frontend y puede mostrar otra interpretación. La guía de fertilización explica este límite.

La búsqueda superior filtra el contenido de la vista que la admite: registros, tareas, comparaciones por bloque y miembros. No es un buscador global del servidor. Los controles de finca y fecha se muestran en el encabezado de escritorio y sobre el contenido en móvil. La fecha seleccionada se usa para la lista de tareas, con pendientes de días anteriores.

Demostración y datos reales

Demostración: tiene una franja visible de identificación. Los datos incluyen una finca, tres campos, cinco bloques, 328 surcos y actividades/tareas de ejemplo. Las modificaciones se guardan en localStorage bajo claves agrovision.*.v1. El rol se puede simular desde Configuración; no altera permisos del servidor. El flujo de tareas no genera eventos reales ni sincroniza datos.

Modo real: usa los endpoints existentes del backend. Los permisos se verifican en el servidor y la UI oculta las acciones de administración a trabajadores. Las tareas, sensores, clima, nutrientes, producción estimada e IA no se sustituyen por valores ficticios en este modo. Los errores del servidor se muestran en pantalla.

En Mi trabajo de hoy → Nueva tarea, administradores, supervisores y agrónomos pueden elegir un campo o bloque y asignar un miembro real de la finca. No es necesario crear bloques para asignar tareas a los siete campos de Guasita. Los trabajadores solo consultan y ejecutan sus asignaciones. El flujo es pendiente → en curso → por revisar → completada; se puede reportar un bloqueo con motivo y retomarlo. Administradores, supervisores y agrónomos pueden aprobar o devolver tareas en revisión. Las tareas y notas persisten en PostgreSQL y las actualizaciones simultáneas se rechazan con un aviso para recargar. La fecha se interpreta según el calendario del dispositivo; todavía no hay zona horaria configurada por finca. Completar una tarea no crea un evento agrícola, ni adjunta evidencias. No hay reprogramación, cancelación o edición de asignaciones en esta primera versión.

Los mapas de demo utilizan una imagen aérea ficticia y polígonos ilustrativos. No son cartografía georreferenciada. La vista real usa Leaflet para colocar los polígonos SRID 4326 de campos y bloques y las líneas SRID 4326 de los surcos encima de un mapa base. La capa Mapa usa OpenStreetMap; Satélite usa World Imagery de Esri por defecto y Híbrido combina ambas capas. Para producción se puede configurar un proveedor autorizado con VITE_MAP_SATELLITE_TILES_URL y VITE_MAP_SATELLITE_ATTRIBUTION. Los campos, bloques y surcos se pueden activar o desactivar desde Herramientas y las geometrías son seleccionables aunque todavía no existan observaciones. Las geometrías marcadas [PRUEBA] se identifican como ficticias en la vista de mapas. Ver el plano de prueba de Guasita.

El endpoint de eventos no devuelve los detalles de observación: los síntomas y la severidad se envían al crear el registro, pero el frontend no inventa esos datos al consultarlo. Las referencias S3 anteriores se conservan. La sección Fotos adjuntas del detalle de eventos e inspecciones permite elegir JPEG/PNG desde archivos o cámara, ampliar miniaturas y descargarlas. En inspecciones se pueden asociar a un tratamiento. Se admiten hasta 10 MB y 24 megapíxeles por foto. Las fotos reales se guardan en PostgreSQL con sesión y CSRF; las demo se guardan en IndexedDB, persisten al recargar y se limpian al restablecer la demo. Primero guarda el registro y luego abre su detalle para adjuntar fotos. No se ofrecen botones de edición para recursos cuyo API solo admite creación, consulta y eliminación.

La estimación de área utiliza las áreas de campos cuando existen, evitando sumar también las áreas de sus bloques. Las plantas son estimaciones agregadas por surco.

Sesión y despliegue

  • api.ts obtiene el token CSRF antes de una escritura y lo renueva después del login. Envía cookies con credentials: include.

  • Las credenciales y los tokens de autenticación no se guardan en localStorage. sessionStorage conserva únicamente la intención de recuperar una sesión real.

  • Las fuentes y la imagen aérea de demostración se incluyen localmente mediante Fontsource y public/images. El mapa real sí carga teselas externas: OpenStreetMap para el mapa base y Esri World Imagery para satélite/híbrido por defecto. Revisa atribución y condiciones de uso del proveedor antes de producción; los endpoints VITE_MAP_SATELLITE_TILES_URL y VITE_MAP_SATELLITE_ATTRIBUTION permiten configurar las teselas satelitales.

  • Para producción, ejecutar npm run build y servir dist/ con un proxy /api hacia Spring Boot. AGRO_API_URL configura el proxy de Vite, no el bundle estático.

  • Usar HTTPS, cookies seguras y el frontend/API en el mismo sitio. No publicar los valores de base de datos de desarrollo como configuración de producción.

  • Las tareas locales no ofrecen sincronización, resolución de conflictos ni garantía de persistencia si el navegador elimina sus datos. No es una PWA offline.

Verificación

Para ejecutar las pruebas de backend, frontend y el recorrido automatizado de una finca temporal en Chrome, usa python3 scripts/run_qa_tests.py desde la raíz. Consulta los requisitos y los informes en la guía de pruebas automatizadas.

npm test
npm run build
npx playwright install chromium
npm run test:e2e

Las pruebas unitarias verifican separación por finca, métricas, fecha local, selección de tareas, transiciones y escape de CSV. Playwright verifica navegación, mapas, formularios, tareas, permisos de la UI, CSV y el intercambio de login/CSRF con un API simulado, tanto en escritorio como en móvil.

Para el recorrido contra un API real, usar exclusivamente una base de verificación aislada: la prueba crea una cuenta, finca, campo, bloque, surco y evento.

AGRO_LIVE_TEST=1 npm run test:e2e -- --project=desktop --grep 'real server onboarding'

El API incluye correcciones de integración para serializar geometrías como GeoJSON y evitar propiedades internas de proxies Hibernate, mapear el enum de eventos y los campos JSONB de PostgreSQL, y consultar eventos asociados solo a bloque o solo a surco con filtros opcionales. Las pruebas del backend cubren ese recorrido y el registro de observaciones/mapas/referencias de archivos.

También se puede usar Chrome instalado en macOS:

PLAYWRIGHT_CHROMIUM_EXECUTABLE='/Applications/Google Chrome.app/Contents/MacOS/Google Chrome' npm run test:e2e
