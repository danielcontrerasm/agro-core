Agro Core is a farm-scoped agricultural operations API, and AgroVision is its Spanish-language web interface. Together they cover farm setup, field work, crop cycles, irrigation, nutrient management, inspections, production records, and agricultural maps.

This repository contains an MVP with a local demonstration mode and a server-backed mode. Demo data is visibly labeled and isolated from real farm records. The system records agricultural workflows and technical reviews; it does not claim to automate agronomic diagnosis, prescriptions, or decisions.

AgroVision frontend

The React / TypeScript / Vite frontend includes responsive desktop and mobile layouts, a sidebar, global view search, farm selection, and these screens:

  • Dashboard with farm metrics, recent activity, interactive map, and charts.

  • Daily work with filtering, farm-member assignment, field/block targeting, creation, execution, blocking, review, and approval persisted in PostgreSQL.

  • Farm maps with interactive fields, blocks, and rows, zoom, filters, layer controls, and health, moisture, nutrient, and disease-observation views. The moisture and nutrient views include legends, summaries, and traceability tables. Demo mode can split the illustrated map to compare two layers. Real mode draws stored geometries over satellite imagery by default, with a hybrid option and an OpenStreetMap plan.

  • Fields with map and list views, a farm hierarchy, field details, and a field-specific block list. In connected mode the map uses recorded geometry. Creation forms, parent filters, and confirmed deletion follow farm permissions.

  • Rows and plants with a block-filtered inventory of row length, spacing, and estimated plant counts.

  • Planting cycles, site/material approvals, planting execution, establishment, and regional planting calendars. The selected cycle shows planned dates, recorded milestones, and its associated block. Ver calendario opens the regional rules.

  • Irrigation overview with recorded consumption, pending volume, sector map, alerts, and a searchable sector table. The module includes readings, recurring scheduling, executions, water administration, and usage reports.

  • Fertilization overview with record counts and a block filter for soil/foliar analyses, approved plans, applications, and technical follow-up. Farm profiles and product catalogs are available to authorized roles in connected mode.

  • Pest/disease inspections, periodic monitoring, incidence alerts, treatment authorization and verification, preventive assignments, and event history.

  • Structured crop-cycle harvest records alongside legacy harvest events.

  • Event creation and detail, authenticated photo uploads, legacy media references, filtered CSV export, and authorized deletion.

  • Agronomic center, account details, farm information, and team role assignment.

  • Registration and login with session cookies and automatic CSRF handling.

Run the frontend

Requires Node.js 22.18+ and npm. From the repository root:

cd frontend
npm ci
npm run dev

Open http://127.0.0.1:5173/#harvest to open the structured Cosecha screen directly. The app starts in a visibly labeled demonstration that works without the Java API. Use Conectar mi finca to register or log in to the real backend. API requests are proxied from /api to http://localhost:8080; override the target with AGRO_API_URL when launching Vite if needed.

Demo changes are stored in this browser under agrovision.* local-storage keys. Real authentication uses HTTP-only server session cookies, not local-storage tokens. The real mode does not substitute demo tasks, sensors, yields, or AI results when the backend lacks those features. The aerial demo map is an AI-generated illustration, not satellite imagery of an actual farm.

npm test
npm run build
npx playwright install chromium
npm run test:e2e

The production build is written to frontend/dist. Production hosting needs an /api reverse proxy to the backend and same-site session cookies. The Vite development proxy is not included in the production build. See frontend/README.md for screens, limitations, and testing.

Implemented features

Farm, field, block, and row management

The location hierarchy is Farm → Field → Block → Row.

ResourceOperationsStored informationList filters
FarmCreate, list, retrieve by ID, deleteName, country, region, creation timestampCurrent user's farm memberships
FieldCreate, list, retrieve by ID, deleteParent farm, name, polygon boundary, supplied area in hectares, creation timestampfarmId
BlockCreate, list, retrieve by ID, deleteParent field, code, crop (defaults to banana), variety, polygon boundary, supplied area in hectares, creation timestampfieldId
RowCreate, list, retrieve by ID, deleteParent block, row code, geographic line, supplied length in meters, plant spacing (defaults to 2 meters), estimated plant count, creation timestampblockId

Lists are restricted to farms the user belongs to. Block codes are unique within a field; row codes are unique within a block. Areas, lengths, and estimated plant counts are supplied by the client rather than calculated automatically. There are no update endpoints for these resources.

Agricultural events and work history

  • Create, search, retrieve by ID, and delete agricultural events.

  • Record occurrence time, notes, optional GPS location, and creation timestamp.

  • Link an event to a block, a row, or both. When both are supplied, the row must belong to that block.

  • Identify an affected plant range using plantIndexStart and plantIndexEnd; individual plants are not separate managed records.

  • Record the authenticated user as the event author.

  • Search using optional farmId, blockId, rowId, eventType, from, and to filters. Date bounds are inclusive and use timestamps such as 2026-10-16T00:00:00Z.

Supported event types:

TypePurpose
SCOUTING_OBSERVATIONRecord crop inspections and suspected pest/disease observations
TREATMENT_APPLICATIONRecord that a treatment was applied
FERTILIZER_APPLICATIONRecord that fertilization occurred
IRRIGATION_EVENTRecord that watering/irrigation occurred
HANDLING_EVENTRecord crop handling activities
SOIL_SAMPLERecord that a soil sample was taken
HARVEST_EVENTRecord that harvesting occurred

These event records are separate from scheduled work tasks and preserve the activity history. Structured crop monitoring data is stored through the monitoring-record API described below. Events default to status OPEN, with no status-transition endpoint.

Scouting observations

  • Attach suspectedCatalogId, severity, and symptoms to a scouting event when an observation payload is provided.

  • Associate the observation with a block, row, or plant range through its event.

  • Store a suspected catalog reference; the dedicated inspection workflow also uses the managed phytosanitary catalog and only active problems can be used for new inspections.

The database includes an ai_diagnosis_json column, but there is no implemented AI diagnosis service or API workflow. Observation details are persisted on event creation; there is no separate observation read/update endpoint.

Disease map layer

  • Return a GeoJSON FeatureCollection containing row LineString geometries.

  • Include rowId, rowCode, maximum severity, observation count, and latest observation timestamp for each returned row.

  • Filter by optional farmId, from, and to, within the user's farm access.

  • Include rows with associated scouting observation details; this is an observation-based summary, not a confirmed disease diagnosis or prediction.

The backend supplies map data; it does not include a map viewer.

Media records

  • Register media references against an existing event.

  • Store media kind, S3 object key, content type, capture timestamp, optional GPS location, and JSON metadata.

  • List media records by eventId.

The legacy /media module stores references and metadata. Actual JPEG/PNG photos are uploaded, viewed, and downloaded through /photos, described below. S3 client integration and presigned URLs are not implemented. There are no media-reference update or delete endpoints.

Fotos de eventos, inspecciones y tratamientos

Desde el detalle de un evento o inspección se pueden elegir fotos, usar la opción de cámara del dispositivo, ver miniaturas, ampliar y descargar las imágenes. En inspecciones se puede seleccionar un tratamiento como destino de la foto. Primero se guarda el registro y después se adjuntan las fotos desde su detalle.

Las fotos reales se guardan como datos binarios en PostgreSQL mediante la migración V8; no requieren S3 ni un directorio compartido de archivos. Los respaldos de la base deben incluir photo_asset. Las claves S3 anteriores siguen disponibles como referencias externas y no se convierten automáticamente en fotos cargadas.

EndpointComportamiento
POST /api/v1/photosMultipart con file y eventId o inspectionId; treatmentId opcional para inspecciones
GET /api/v1/photosLista metadatos según el mismo destino, sin devolver los bytes
GET /api/v1/photos/{id}/contentImagen autenticada; ?download=true fuerza descarga

La carga admite JPEG y PNG de hasta 10 MB y 24 megapíxeles; hasta 10 fotos por selección, enviadas individualmente. El navegador aplica la orientación de la imagen y la prepara para carga. El servidor verifica el contenido real y las dimensiones, decodifica y vuelve a codificar la imagen sin metadatos originales. Se conserva el nombre del archivo saneado, formato, tamaño, autor y fecha de carga. Cada carga, consulta y descarga exige sesión y pertenencia a la finca; las cargas usan CSRF. Las respuestas de imagen tienen no-store y nosniff.

Una inspección anulada conserva sus fotos consultables, pero no admite más cargas. Al eliminar un evento se eliminan sus fotos por cascada. El modo demo guarda los blobs en IndexedDB, separados de los datos reales, conserva las fotos al recargar y las limpia al restablecer la demostración. Al eliminar eventos demo también se eliminan sus fotos. Las cargas fallidas muestran error y conservan las fotos que ya se guardaron en una selección múltiple.

Authentication and authorization

  • Register users and log in/out using HTTP sessions.

  • Retrieve the current user's profile and farm memberships.

  • Store BCrypt password hashes and normalized email addresses.

  • Protect state-changing requests with CSRF tokens; rotate session IDs and CSRF tokens at login.

  • Assign ADMIN, SUPERVISOR, AGRONOMIST, and WORKER roles independently for each farm.

  • Automatically give farm creators the administrator role on their new farm.

  • Let administrators add registered users to their farm or change their roles.

  • Restrict farm resources, events, media, and map results to farm members.

See the permissions table and onboarding examples below for the complete flow.

Geospatial storage and infrastructure

  • PostgreSQL/PostGIS storage with spatial indexes and SRID 4326 coordinates.

  • Point, polygon, and line input DTOs, with automatic closure of polygon rings; only the outer polygon ring is supported.

  • Spring Data JPA persistence, Hibernate Spatial, and JTS geometry conversion.

  • Flyway migrations evolve the schema from core farm/identity tables through planting, task, irrigation, fertilization, inspections, photos, and production workflows (currently through V24, with version gaps).

  • Basic request validation for required fields and authentication inputs.

  • Swagger/OpenAPI documentation and interactive API exploration.

  • Spring Boot Actuator health endpoint at /actuator/health.

  • Configurable browser CORS origins and session cookie settings.

  • Docker Compose database setup with persistent database storage.

  • Gradle wrapper and automated authentication, permission, membership, and application startup tests.

JPA persistence

Spring Data JPA repositories manage mapped records, including account creation and normalized email lookup through AppUserRepository. The block map uses a typed harvest projection from CropMonitoringRecordRepository for harvested quantity, estimated yield, and growth stage. Account repository · Monitoring repository

JpaSql uses JPA's EntityManager for native SQL. It binds parameters and maps report rows, handles generated IDs, and runs writes in Spring-managed JPA transactions. PostgreSQL queries use features such as FOR UPDATE for row locks, ON CONFLICT for membership upserts, and RETURNING for generated IDs. Farm creation stores the farm, creator membership, and initial catalog entries in one transaction. Flyway manages the database schema. Native query adapter

The H2 API tests create isolated schemas through JPA and use a JpaTransactionManager. The QA runner executes the PostGIS tests and the Chrome walkthrough against a disposable database. JPA test configuration

Functional requirements

Functional requirements describe what users can do and what the system must do in response. For example, a worker signs in, sees their assigned work, and records its completion. The statuses below distinguish current behavior from work that still needs development:

  • Implemented: available in the current backend.

  • In progress: the core workflow exists, but important capabilities remain incomplete.

  • Partial: some of the requirement is available, while one or more specified behaviors remain missing.

  • Missing: no usable end-to-end implementation exists yet.

  • Planned: missing work that is identified for a future delivery.

For cross-product functional and non-functional requirements, status, and open gaps, see System Requirements. The detailed crop-management audit tracks its own workflow, endpoint inventory, and evidence. Module documentation is available for fertilization and water management.

In this section, Partial means some controls exist but the full requirement has not been implemented or verified. Proposed target means a planning value that needs agreement and measurement, not a current service guarantee.

Performance, availability, and recovery targets must be confirmed against the expected farm count, worker count, data volume, connectivity, deployment budget, and business needs. No performance, uptime, or recovery certification is implied by the current automated tests.

System diagrams

These diagrams preserve a useful view of the core identity, farm, geometry, and event model. They are conceptual and do not show every domain table or relationship. The current Flyway schema spans migrations V1 through V24 (with gaps), including tasks, planting, irrigation, fertilization, inspections, photos, and production. The architecture and component diagrams show the current single API service at a high level. The diagrams use Mermaid; open this file in a Markdown viewer with Mermaid support to render them.

Entity relationship diagram

farm_membership has a composite primary key (farm_id, user_id). Additional unique constraints are (field_id, code) on blocks and (block_id, row_code) on rows. An event must reference at least a block or a row; the API requires a matching block when both are supplied. created_by_user_id is populated from login but has no database foreign key, so historical author IDs remain intact.

Sequence diagram — login and farm access

This example starts with an existing registered user. A worker needs an assigned farm membership before farm data appears in their list.

Requests without authentication are rejected with 401 on protected endpoints; missing or invalid CSRF tokens on writes return 403. Access to a farm outside the user's membership, or an operation outside their role, returns 403.

Architecture diagram

The application is a single Spring Boot service with domain modules for identity, farm structure, tasks, planting, events, inspections/prevention, monitoring, irrigation, fertilization, telemetry, analytics, media, and photos. PostgreSQL stores agricultural and identity data; HTTP authentication sessions remain in application memory.

The legacy media module stores S3 keys; photo uploads use the PostgreSQL-backed photo service. Swagger UI is served by the API; the AgroVision frontend runs separately through Vite or its static production build.

Component diagram

This component view uses a Mermaid flowchart to show the core identity, farm, event, geometry, and persistence dependencies. It is not an exhaustive map of the current domain packages. Some controllers read/write repositories directly; there is not a service layer between every controller and persistence.

Entities and DTOs belong to their respective domain packages. Farm creation also inserts the creator's administrator membership in the same JPA transaction as the farm record. FarmAccess resolves resource ownership and checks farm roles against the database on each request that uses it.

Prerequisites

  • JDK 17. The Gradle toolchain requires Java 17 specifically; a newer JDK alone does not satisfy it.

Crop catalog

Each farm has a reusable crop and variety catalog. Administrators, supervisors, and agronomists can add catalog entries from Configuración → Catálogo agrícola; workers can select the approved entries when creating blocks, crop cycles, and planting material lots. Existing crop and variety text is retained for compatibility, while new records also store catalog identifiers. Existing farms are seeded with Banano / Cavendish and prior text values are migrated into catalog entries.

Regional planting calendars

Each farm can configure recurring planting rules by region, crop, and optional variety from Configuración → Calendario regional. Annual rules store a month/day window and preparation lead time; perennial rules support continuous production without an annual season. The suggestions endpoint resolves the farm's region and prioritizes variety-specific rules over crop-wide rules. When a matching annual rule exists, cycle creation rejects a planting window outside the configured regional window; farms without rules remain compatible with manually planned cycles.

Crop management status

This status covers crop management only: crop and variety catalogs, planting cycles, lote evaluation, planting plans, field execution, establishment, phenology, regional calendars, and agronomist access. Nutrient, water, pest/disease, and production management are separate modules and are not included in this estimate.

Estimated coverage: approximately 80%. This is a functional estimate, not a test-coverage percentage: the core workflow is usable, while automation, richer catalog data, permissions, and auditability remain incomplete.

Implemented

  • Farm-scoped crop and variety records with catalog selection in planting workflows.

  • Crop-cycle creation by block with planting dates, expected harvest, and stage data. Planting plans store planned area and density. Execution records store actual area and plant counts.

  • Site/lote assessment with approval and rejection actions.

  • Planting-material lot registration with accept/reject decisions.

  • Planting-plan creation, approval, task creation, and field execution records.

  • Establishment checks for survival, mortality, and replacement, with dated follow-up notes.

  • Phenological stage observations and cycle stage history.

  • Regional annual/perennial planting rules, suggestions, and cycle-window validation.

In progress

  • Crop and variety catalog lifecycle, including richer agronomic attributes and edit/archive behavior.

  • Automatic cycle-stage progression, replant links, and planned-versus-actual cycle reconciliation.

  • Reusable calendar templates and stronger preparation, planting, and replanting workflows.

  • Agronomist role access and approvals; the current model is still role-wide.

Missing

  • Calendar- and growth-stage-driven automatic task generation with recurrence and duplicate protection.

  • Fine-grained agronomist permissions by capability, module, region, or time period.

  • A unified, immutable crop-management audit timeline across approvals and record changes.

Planned next

  1. Complete crop/variety catalog lifecycle and agronomic reference attributes.

  2. Automate crop-stage transitions and calendar-driven preparation, planting, and replanting tasks.

  3. Add delegated and time-bound agronomist permissions.

Crop monitoring records

/api/v1/monitoring-records stores structured records against a field, block, or row. Every record has a recordType, recordedAt, and location; non-harvest monitoring records still require a block. Supported types are CROP_CYCLE, SOIL_SAMPLE, FERTILIZER_APPLICATION, IRRIGATION, HEALTH_OBSERVATION, and HARVEST.

The request supports crop and variety lifecycle fields; soil pH and N/P/K values; nutrient deficiencies; fertilizer product, dose, and quantity; irrigation duration, water volume, and soil moisture; pest or disease, severity, symptoms, prevention, treatment, follow-up, and resolution; and estimated/actual yield, quality grade, and rejected quantity, rejection reason, harvested area, and crop-cycle linkage. Harvest units are controlled (g, kg, t, lb, cajas, racimos, unidades) and quality grades are controlled (PREMIUM, A, B, C, REJECTED). Records can be filtered by farmId, blockId, fieldId, cropCycleId, recordType, from, and to. Farm membership is enforced for reads and writes, while deletion requires an agronomic role.

The Cosecha y producción screen uses structured HARVEST records rather than the legacy generic HARVEST_EVENT activity form. It captures the location hierarchy, cycle, explicit harvest date, area, estimate, actual quantity, unit, quality, rejected quantity, rejection reason, and notes, and shows per-unit totals plus estimated-versus- actual variance. Each record can be opened in a detail view or edited through PATCH /api/v1/monitoring-records/{id} with the same validation rules as creation. Existing generic harvest events remain available in the activity history for backward compatibility.

Sensors, alerts, and analytics

Inspecciones fitosanitarias

La pantalla Plagas y enfermedades permite registrar inspecciones por bloque y surco opcional. El catálogo inicial incluye Sigatoka negra, moko, marchitez por Fusarium, bacteriosis, picudos y nematodos; ahora puede administrarse desde Configuración → Catálogo fitosanitario. Se registran fecha, plantas inspeccionadas/afectadas, área afectada en hectáreas, síntomas, severidad porcentual con método de evaluación y próxima visita. La identidad autenticada determina el responsable.

La incidencia se calcula como 100 × afectadas / inspeccionadas; es incidencia por plantas de la muestra, no por área. El área afectada se captura explícitamente en hectáreas y, cuando el bloque tiene área configurada, no puede superarla. No se infiere un diagnóstico ni un tratamiento. Todas las inspecciones se crean como sospechosas. Administradores y supervisores pueden confirmar, descartar o marcar un hallazgo resuelto dejando justificación, responsable y fecha de revisión. Las versiones evitan sobrescribir revisiones concurrentes. Los resultados confirmados deben sustentarse en la evaluación técnica correspondiente; este módulo no verifica resultados del ICA.

La capa de salud usa la última inspección por problema y destino (bloque/surco). Una evaluación se considera reciente hasta la próxima visita y como máximo por 30 días desde la inspección, con fechas de referencia UTC. Este límite operativo no es una frecuencia agronómica recomendada. Rojo significa hallazgos activos; verde, muestra reciente sin hallazgos activos; gris, falta de evaluación reciente. Las evaluaciones antiguas o resueltas no mantienen el bloque rojo. Un hallazgo activo vencido conserva el estado desconocido aunque exista una evaluación reciente de otro problema. El resumen no certifica sanidad de todo el bloque. Los eventos antiguos se conservan como historial y no colorean esta capa.

Pruebas aisladas sin PostgreSQL: ./gradlew test --tests com.yourco.agro.InspectionApiTest. Prueba de navegador: cd frontend && npx playwright test tests/inspections.spec.ts.

Medidas preventivas

Tratamientos, evidencias y conservación del historial

La pantalla conserva dos pestañas: Inspecciones e Historial anterior y tratamientos. La segunda recupera la consulta, captura de eventos, referencias de archivos, exportación CSV y eliminación autorizada del flujo anterior; no se migran ni eliminan los eventos existentes.

Desde el detalle de una inspección se registran tratamientos realizados con fecha, descripción, producto opcional y cantidad/unidad opcionales. Las cantidades y unidades deben informarse juntas. Una evidencia puede referenciar la inspección o uno de sus tratamientos. Se conserva el autor autenticado. Estas evidencias son referencias S3 y metadatos. La sección Fotos adjuntas permite además cargar, ver y descargar fotos reales, independientemente de esas referencias.

Los tratamientos nuevos se almacenan vinculados a la inspección, se consultan y exportan desde su detalle y no se duplican como eventos genéricos. El seguimiento crea una nueva inspección enlazada a su origen, con el mismo problema y ubicación. El detalle permite navegar entre el origen y sus seguimientos.

Los gestores pueden anular, con motivo y versión vigente, en lugar de borrar una inspección. Se conservan fecha, autor, motivo, tratamientos y evidencias; la inspección anulada se excluye de la capa de salud y no admite más revisiones, tratamientos, evidencias ni seguimientos nuevos. Sus seguimientos existentes conservan su propia evaluación. La anulación no equivale a resolver un hallazgo.

Sensor devices belong to a farm and can optionally target a block. Devices ingest timestamped readings for soilMoisture, airHumidity, airTemperature, and soilTemperature through /api/v1/sensors/{deviceId}/readings. Readings are retained for history and can be polled by time range; the ingestion API is ready for an IoT gateway or MQTT/HTTP adapter.

Managers can create alert rules using a metric, LT, LTE, GT, or GTE operator, threshold, severity, and message. Matching readings create open alerts that users can list by farm/status and acknowledge. This provides threshold-based moisture, temperature, and humidity alerts without making agronomic decisions automatically.

/api/v1/analytics/map returns a GeoJSON block layer with the latest telemetry, condition status (DRY, OPTIMAL, WET, or NO_DATA), harvest totals, and pest-risk severity. /api/v1/analytics/dashboard?farmId=1 returns block count, fertilizer quantity, water volume, harvested quantity, health observations, open alerts, and connected-device counts. /api/v1/analytics/water-usage returns date-scoped planned and actual irrigation volume by sector/block, measured versus estimated consumption, rainfall, balance requirements, deficits, and soil-moisture reading context for the Reports screen. Suitability and recommendation models remain domain rules to be calibrated with agronomists; current condition and risk scores are transparent threshold-based summaries.

Example onboarding

Keep the cookies returned by the server and send the CSRF token in X-CSRF-TOKEN for every POST, PUT, PATCH, or DELETE request, including registration and login.

curl -c /tmp/agro-cookies.txt http://localhost:8080/api/v1/auth/csrf

Copy the response's token value into CSRF_TOKEN, then register and login:

CSRF_TOKEN='paste-token-here'
curl -b /tmp/agro-cookies.txt -c /tmp/agro-cookies.txt \
  -H "X-CSRF-TOKEN: $CSRF_TOKEN" -H 'Content-Type: application/json' \
  -d '{"name":"Farm Owner","email":"owner@example.com","password":"replace-this-password"}' \
  http://localhost:8080/api/v1/auth/register

curl -b /tmp/agro-cookies.txt -c /tmp/agro-cookies.txt \
  -H "X-CSRF-TOKEN: $CSRF_TOKEN" -H 'Content-Type: application/json' \
  -d '{"email":"owner@example.com","password":"replace-this-password"}' \
  http://localhost:8080/api/v1/auth/login

Login rotates the session ID and CSRF token. Fetch /api/v1/auth/csrf again using the updated cookies and replace CSRF_TOKEN with the new token before writing. Create a farm with POST /api/v1/farms and {"name":"My Farm"}. Have the worker register their own account, then assign them from the owner's session:

curl -b /tmp/agro-cookies.txt -c /tmp/agro-cookies.txt \
  -X PUT -H "X-CSRF-TOKEN: $CSRF_TOKEN" -H 'Content-Type: application/json' \
  -d '{"email":"worker@example.com","role":"WORKER"}' \
  http://localhost:8080/api/v1/farms/1/members

Replace 1 with the created farm ID. The worker's login response and /auth/me will include that farm and role. Role changes take effect on existing sessions.

Configuration and existing data

  • Sessions expire after eight hours of inactivity and are stored in server memory; restarting the API requires users to log in again.

  • Set SESSION_COOKIE_SECURE=true when serving the API over HTTPS in production.

  • Browser clients must send requests with credentials. CORS allows http://localhost:3000, http://localhost:5173, and http://127.0.0.1:5173 by default; configure APP_CORS_ALLOWED_ORIGINS as a comma-separated list for other origins.

  • Cookies use SameSite=Lax. A frontend hosted on a different site requires a deployment-specific cookie configuration; using a same-site API proxy avoids this.

  • Migration V2 preserves existing agricultural data. Existing farms have no owner assigned automatically. A database operator must assign their initial administrator after that user registers, using the correct farm ID and email:

INSERT INTO farm_membership (farm_id, user_id, role)
SELECT 1, id, 'ADMIN' FROM app_user WHERE email = 'owner@example.com';

Persistent work tasks

Migration V3 introduced tasks stored in PostgreSQL. Administrators, supervisors, and agronomists can create tasks assigned to a member of the same farm, targeting exactly one field or block. Workers list and update their assignments; agronomic managers list and review tasks in their farms. The UI includes selected-day and outstanding overdue work using the device calendar. Tasks are separate from agricultural events and from browser demo data.

EndpointBehavior
GET /api/v1/tasks?farmId=1List authorized tasks; farm filter optional
POST /api/v1/tasksCreate with farmId, fieldId or blockId, assigneeId, title, activity, date, time, priority, instructions
PATCH /api/v1/tasks/{id}Update status, optional notes, and required current version; stale updates return 409

Activities: fertilization, irrigation, scouting, planting, harvest. Priorities: Alta, Media, Baja. States: pending → progress → review → completed. Pending/in-progress tasks can become blocked with a reason and resume as progress. ADMIN, SUPERVISOR, and AGRONOMIST can approve or return reviewed tasks to progress; a return reason is not currently required. Completing a task does not create an agricultural event. The PATCH endpoint changes task status and notes with an optimistic version; it does not edit assignment/details, reschedule, cancel, delete, attach evidence, or expose transition history.

python3 scripts/run_qa_tests.py
